# Isoplan plugin

Isoplan is a live view of every agent working across a team, drawn as an office floor. This repo holds the open part of it: the Claude Code plugin that streams each session's facts to a team's office server, and the wire protocol between them. Both are MIT, so anyone can check exactly what runs on their machine and what it sends.

The office server and the floor are a separate, proprietary product.

## Install the plugin

This repo is a Claude Code plugin marketplace. In Claude Code:

```
/plugin marketplace add isoplan-app/isoplan-plugin
/plugin install isoplan@isoplan
```

Then connect it to your office: start a Claude Code session once, so the plugin sets itself up, then on the office's floor open **Settings → Connect Claude Code** and press the button. Your browser asks to open Isoplan, and this computer asks, in a dialog naming the office's address first, then the person the machine will report as and what the office calls itself, whether to connect. Check the address and that the person is you (a link someone else made reports as them), and press **Connect**; Cancel is the default, and the dialog cancels itself after five minutes. The plugin then adds the office to `servers` in `~/.claude/isoplan/config.json` and pairs the machine; sessions report to it from their next prompt.

The plugin handles those `isoplan://connect` links itself. Installing it (as each session starts, and the install script) copies the handler to `~/.claude/isoplan/runner/app/dist/connect.mjs` and registers it for you alone, with no admin rights: on Windows under `HKCU\Software\Classes\isoplan`, named Isoplan, through a small launcher, `~/.claude/isoplan/open-link.js`, that Windows Script Host runs to hand the link to node with no window (where Script Host is turned off, node runs directly, and a console window shows for a moment); on a Mac as a small app, `~/.claude/isoplan/Isoplan Connect.app`, registered with LaunchServices; on Linux as `~/.local/share/applications/isoplan-connect.desktop`, made the default for `x-scheme-handler/isoplan` with `xdg-mime` (and its dialog needs `zenity`). It is registered only when nothing is, or what is names a node or a handler that has gone, so with several config folders on one machine the first keeps the link until its registration breaks; on Windows, an older registration that runs node directly is redone once through the launcher, by whichever config folder starts a session first. The handler accepts only an office at `https://`, or `http://` on this computer, handles one link at a time, and changes nothing unless you press Connect; what it did, or why not, is also in `~/.claude/isoplan/logs/connect.log`.

In a session, `/isoplan:connect` says which offices this computer is connected to: those in `servers` it holds a credential for, never the credential. `/isoplan:connect <isoplan://connect link>` connects with a link from the floor instead of the browser, and says in the conversation how it went: it runs `dist/connect.js --wait <link>`, which starts the handler as above with a random run id that tags its lines, then reads that run's lines in `connect.log` for up to 310 seconds, the dialog's five minutes and a little (the command asks for a 330-second timeout). It says only fixed sentences, never an office's own words, so a link from an untrusted office can't put text into the conversation. The floor's set-up message runs the same, since the command only loads in a new session.

Or do it by hand: set `server` in `~/.claude/isoplan/config.json`, for example `{ "server": "wss://your-office.example/data-layer" }`, then pair with the link the status line shows. Any key in that file overrides the plugin's defaults in `packages/mod/config.json`.

To report to several office servers at once, list them under `servers` instead, each with a short label for the status line:

```json
{
  "servers": [
    { "label": "internal", "server": "wss://internal.example/data-layer" },
    { "label": "dev", "server": "ws://127.0.0.1:4747/data-layer" }
  ]
}
```

A session then reports to every one of them whose office takes its repo, and to none otherwise, and the status line names each one it reports to, as in `Isoplan: internal ✓ · dev ✓`. An office is named there only once its list is known to take the repo, or while it waits for this machine to be paired, so outside every office there is no status line at all. A plain `ws://` server to another machine (see below) is named only when its last list takes the repo, or when there is no list to tell by, which the status line says. Each server is on its own: its pairing, its list of repos, the session's link and its state, the reports held for it, the runner's link, asking the earlier session, owner answers and handoffs, so a server that can't be reached, is slow to answer, or waits to be paired leaves the others as they are. An entry without a label is named by its host, and a label used twice gets `-2` after it. An entry is used when its `server` is a `ws://` or `wss://` address; while `servers` has one, `server` is ignored. Changing either takes effect for a session at its next start.

### Updates

The plugin keeps itself up to date with each release (see Release): Claude Code installs a new copy only when the version in the plugin's `plugin.json` changes. As a session starts (unless a session on the machine checked in the last ten minutes) and every `updateCheckHours` (6) after that, the plugin runs `claude plugin marketplace update isoplan`, then `claude plugin update isoplan@isoplan --scope <scope>` for each scope it is installed at (a project's in that project's folder), in the background, hidden, with the `claude` binary the runner uses, one check at a time on the machine (`~/.claude/isoplan/update.json` and `update.lock`). The commands never prompt: git asks for no password and opens no credential window, ssh runs in batch mode, and a command still running after five minutes is stopped with everything it started. It also turns on Claude Code's own auto-update for the marketplace, by adding `"autoUpdate": true` to the `isoplan` entry under `extraKnownMarketplaces` in your `~/.claude/settings.json`, the entry `/plugin marketplace add` wrote; it leaves an entry that says `"autoUpdate": false`, adds no entry that isn't there, and uninstall takes it out only from an entry nothing has changed since the plugin added it (otherwise auto-update stays on).

### Installs from before the move

This repo moved from `adamlinscott/isoplan-plugin` to `isoplan-app/isoplan-plugin`. A marketplace added under the old name keeps updating through GitHub's redirect. To move it by hand, paste this into Claude Code:

```
Isoplan's plugin marketplace moved from adamlinscott/isoplan-plugin to isoplan-app/isoplan-plugin. Move my install, in this order. 1. In my user settings.json in Claude's config folder, note the whole extraKnownMarketplaces.isoplan entry, then change only its source.repo to isoplan-app/isoplan-plugin. 2. Run: claude plugin marketplace add isoplan-app/isoplan-plugin (it fails if run before step 1). 3. That command rewrites the entry as a bare source, so put back every other field the entry had, such as autoUpdate, exactly as it was. Never remove the marketplace: that uninstalls the plugin. 4. Run claude plugin list and tell me whether isoplan@isoplan is enabled.
```

A running session keeps the version it loaded, so once a newer one is on disk the status line says **Isoplan updated: type /reload-plugins** beside the link's state; Claude Code doesn't let a plugin reload itself, or run a command from a click on the status line. Newer means the newest version installed for that session (at user scope, or at project or local scope for its project), counted only once Claude Code has written its folder whole. After the reload the new version's hooks module has the session, and the old one's lets it go; the new one copies its runner into place, which replaces the running one, and records itself for the wake hook. A session left on an older version reports as before but leaves those alone. A new session loads the new version at once. A session open in two windows is reported for the one started later; the other's status line says so, and it takes over again within a minute once that window closes. If Claude Code has cleaned up the old version's folder before you reload, the plugin stops reporting that session and the status line just says to reload.

Set `updateCheckHours` to `0` in `~/.claude/isoplan/config.json` to stop the checks. Nothing is checked while the plugin is disabled for the machine, or while `DISABLE_UPDATES`, `DISABLE_AUTOUPDATER` or `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is set, as with Claude Code's own plugin updates, unless `FORCE_AUTOUPDATE_PLUGINS=1` is set too. A plugin loaded from a folder (a checkout, `--plugin-dir`, or a marketplace added from a local path, which Claude Code loads in place) isn't updated: it runs whatever is in the folder.

The plugin needs Node.js on `PATH`. When it first starts it puts a small hook in your `~/.claude/settings.json` (on `UserPromptSubmit` and `Stop`), which starts the runner (below) whenever it isn't running, and copies the runner into `~/.claude/isoplan/`. The runner reports every session that doesn't load the plugin: headless ones, those you drive from the floor, and terminal sessions without it.

### Pairing this machine

An office server that signs people in reports a machine only once someone has paired it, and what the machine reports is then that person's. The first time a session starts and reads which repos the office takes, Claude Code's status line shows a **Pair this machine** link, such as `https://your-office.example/#pair=...`, and the transcript shows it once per session start. Click it on this computer: the office asks you to sign in if you aren't, shows the machine, the Claude account it names and when it asked, and you approve it. Your browser is then sent back to this machine, to `http://127.0.0.1:<port>/...`, where Isoplan's runner, which asked, is listening, and it finishes pairing there with a secret it never sent. A link sent to someone else can't pair your machine to them, or theirs to you. The plugin never opens a browser itself, and nothing needs typing in a terminal. The runner writes the same link to its log, and to the log of each session it reports without the plugin.

The machine's credentials and access tokens are kept in `~/.claude/isoplan/pairing.json` (in `$CLAUDE_CONFIG_DIR/isoplan/` when that is set), with a random id the machine makes for itself the first time and one entry per office server, readable by you only (on Windows it takes the folder's permissions). Each entry is kept under the Claude account it was paired under, but the pairing is the machine's: after you log in to Claude as someone else, Isoplan keeps using and renewing that entry where it is (with several, the one renewed most recently), and pairs again, under the new account, only when there is none for that office. The entry for the server `server` names (the plugin's default when you set only `servers`), which versions before multiple servers report to, is under `accounts`, where they look; every other server's is always under `offices`, by its address, which is read first, so an older version still running never overwrites it. `pairing.write.lock` beside it is held while the file is changed, and each server's `offices/<id>/pairing.lock` names the one process answering that server's link while one waits to be clicked; the server `server` names (the plugin's default when you set only `servers`) keeps `pairing.lock`, which an older version still running uses for it, so the two never pair it at once. Each server shows its own link to pair, and pairing with one never waits on another. Pointing `server` at a new address pairs the machine with it. The token lasts about an hour and is renewed on its own, and the link reconnects at once when the office closes it as the token runs out. If the pairing is revoked on the floor, or lapses after 30 days without the machine connecting, the next session shows a new link. Deleting the file unpairs the machine on this side; revoke it on the floor too.

A session belongs to the person whose machine first reported it. If the office says it belongs to someone else, the status line says so and the session isn't reported; it asks again an hour later, in case an admin released it.

A credential is never sent over plain `ws://` to another machine: such a `server` isn't used, and the status line says why, unless config.json sets `"allowPlainWs": true`, which sends facts and credentials unencrypted.

One limit can't be designed out: a process already running as you on this machine could start a pairing of its own and show you its link. Approve only a pairing you started on this computer.

A machine with no browser (a headless server) can't be paired yet.

### A session doesn't show on the floor

Run `/isoplan:repos` in it. It asks every office the session reports to (each in `servers`, or `server` without them) now which repos it takes, rather than waiting for the next check (up to `approvedRefreshMinutes`, 5), and says for each, in one sentence, whether it takes the repo of the folder the session reports as, and what to do if not: an admin adds it under Repos on the floor, this computer connects to the office, or the office can't be reached. With no office in your `config.json` it says to press Connect Claude Code. A session with the plugin, or one the runner is reporting, shows on the floor of an office that takes its repo within a minute; one it isn't (a session without the plugin that has gone quiet, or one held off) starts again at its next message, so if it doesn't show, send any message in it. It sends this machine's pairing token as a session would, renewing it and keeping the new one for the sessions when it has run out, never pairs the machine, and never prints a token; what goes wrong is written to `~/.claude/isoplan/logs/repos.log`.

## Disable or uninstall

Claude Code runs nothing of a plugin's when you disable or uninstall it, so the hook in your settings looks for itself, each time a session takes a prompt, at what Claude Code records: `installed_plugins.json`, and `enabledPlugins` in your settings, the project's settings and a `managed-settings.json` file (not managed settings from MDM or the claude.ai console, which it can't read). The project is the session's `CLAUDE_PROJECT_DIR`, or its folder. An install at project or local scope counts only for that project's sessions.

**Disable** it (`/plugin disable isoplan@isoplan`, the plugin manager, or `claude plugin disable`) and reporting stops: the hook stops the runner, which reports every session, and starts nothing. Every file stays, the pairing credential too. Disabled in one project only, that project's sessions aren't reported. Enable it again and the next prompt starts them again.

**Uninstall** it (`/plugin uninstall isoplan@isoplan`, the plugin manager, or `claude plugin uninstall isoplan@isoplan`) and, the next time a session takes a prompt, the hook takes everything out in the background. That happens only once Claude Code lists no install of `isoplan` at all, from any marketplace and at any scope, and no folder in `CLAUDE_CODE_PLUGIN_DIRS` holds it, so moving to another marketplace isn't an uninstall, and Claude Code's records must still say so five seconds later, so an update rewriting them isn't one either. A copy you load with `--plugin-dir` leaves nothing it can find, so remove the marketplace install only once you no longer want it. What it takes out:

- the runner, which it stops;
- the `isoplan://` link handler it registered (see Install the plugin), when it is this config folder's, and its Windows launcher;
- the login item that starts the runner when you log in (see The runner), and its Windows launcher;
- what the plugin wrote in `~/.claude/isoplan/`: the runner's copy and its records (`runner/`: the app, `environment.json`, the ledger, the lock), the machine's pairing credential (`pairing.json`), each office's copy of its list of repos, the lock of a pairing under way and the hashes of reports released on its floor (`offices/`), the one copy and lock a version before multiple servers kept (`approved.json`, `pairing.lock`), the session locks (`live/`), the logs (`logs/`), the title files (`titles/`), the hashes of reports you released, for the office `server` names (`released/`), the marks of the questions a session waits on (`waits/`), owner answers waiting for their session (`answers/`), taken and unsent handoffs' briefs and launchers, and which office each session took its handoff from (`handoffs/`), the update check's record and lock (`update.json`, `update.lock`), the locks of a link handler's or login item's registration that was stopped part way (`link-handler.lock`, `login-item.lock`), the launchers and tasks of sessions started outside the floor (`starts/`), owner messages waiting for their session (`messages/`), GitHub repos' current names (`remote-names.json`), the empty folder git runs with as its hooks (`no-hooks/`), and `claude-binary.json` unless you set it by hand;
- the `"autoUpdate": true` the plugin added to its marketplace's entry in `~/.claude/settings.json`, if nothing in that entry has changed since; otherwise it stays on;
- last, the hook in `~/.claude/settings.json` (every other hook and setting is kept), the hook script and its record (`wake.mjs`, `wake.json`), and the uninstall's own lock and log (`uninstall.json`, `uninstall.log`).

The files you write are kept: `config.json`, `runner.json`, `secret-patterns.json`, and a `claude-binary.json` you set by hand, so a reinstall picks them up again. So are experts' folders (`experts/`) and Isoplan's own clones (`clones/`), which may hold a hidden session's work that isn't pushed yet, wherever `clonesFolder` put them, and the record of the folders it named (`clones-folders.json`). Delete `~/.claude/isoplan/`, and any folder `clonesFolder` named, yourself to take those too; once nothing is left in it, uninstall removes the folder.

It asks Claude Code before each step whether the plugin is still uninstalled, and stops if you installed it again. A session that already had the plugin loaded stops reporting, but Claude Code keeps the plugin loaded there until the session ends or you run `/reload-plugins`; if it wrote its files again meanwhile, the hook stays and the next prompt finishes the job. If it can't finish while the hook is still in place, for example because `settings.json` doesn't parse, it says why in `~/.claude/isoplan/uninstall.log` and the hook tries again a day later; delete `~/.claude/isoplan/uninstall.json` to have the next prompt try at once. If a step fails after the hook has gone, nothing is left to try again: what remains of `~/.claude/isoplan/` stays until you delete it, or until you install the plugin again, which clears it.

Two things it can't help:

- It writes `settings.json` whole, as Claude Code does, and there is no lock to share with Claude Code, so a change Claude Code writes to that file at the same moment can be lost. Check the file if you changed a setting right then.
- A session that was open when the hook went may still run it until that session restarts, and shows Claude Code's non-blocking hook error each turn, since `wake.mjs` has gone.

From a checkout, `pnpm isoplan-uninstall` takes out the same things at once, and leaves `~/.claude/isoplan/wake.json` as `{ "disabled": true }` (written before the hook comes out), so the plugin, if it is still installed, doesn't put the hook back when it next starts, and finishes anything the uninstall left; `pnpm isoplan-install` takes that away. An install waits for an uninstall that is still running.

## The runner

Each machine runs one runner (`packages/mod/dist/runner.js`, which install copies to `~/.claude/isoplan/runner/app/dist/runner.mjs` with its defaults beside it, so a plugin update doesn't delete the files it runs from), which answers the office server's questions and handoff briefs for the machine's sessions. With several servers it holds a link to each, which answers only for that office's sessions; the forks and their one cap (`maxForks`, for the machine whichever office asks), the other caps and the ledger are the machine's, shared by them all. A server that doesn't want the runner closes its own link, asked again an hour later, and one that says the pairing has ended closes its link until a session has paired the machine again; what the runner would have sent it meanwhile waits, at most 100 replies, and goes once the link is back, unless an hour has passed since the runner first sent it. The runner never stops while a fork or a take is still running. It answers from a fork of the lead session: a one-off `claude -p --resume --fork-session` with no tools, no MCP servers, no settings files and none of your Claude Code hooks, which is never saved. Install, the plugin, the wake hook and the login item start it, a newer copy replaces an older one as it starts, and it stops once every session on the machine has gone lights-off, unless it starts at login or is running a session you drive from the floor (below). Before an answer or brief leaves the machine, it is checked for secrets, and one that matches is withheld until you release it from the floor.

The runner is the one Isoplan process on the machine: it reports every Claude Code session on it, with or without the plugin, each on a link of its own to each office, with one list of repos, secret checks, held reports and pairing. A session that loads the plugin keeps only a thin hooks module inside Claude Code, for what has to run there: the status line, the `ask_room` tool, answering a question from the floor, and submitting a message from the floor as the next turn. It reaches the runner over a local pipe, through a small helper it starts (`dist/pipe.js`), since Claude Code gives a hooks module no sockets. The pipe has a new name each time the runner starts (a named pipe on Windows, a Unix socket in a folder of your own under `~/.claude/isoplan/pipe` on macOS and Linux). Where it is, and a token, are in `~/.claude/isoplan/runner/pipe.json`, which only you can read, and the runner takes nothing without that token. On Windows other users can see the pipe's name, so the runner first proves it knows the token, and the plugin sends nothing to a pipe that can't. The runner reports that session from its first turn for as long as its hooks module is connected, and only for that hooks module; once you close it, it goes unreachable on the floor, as before. If the runner isn't running, the helper starts it and tries again every `runnerRetrySeconds` (2), and the status line says the session isn't reaching the office until it's back (or, while the runner is holding off or isn't installed, says that, and so does the session's log); a runner started again has the session back on the floor within a few seconds.

For a session without the plugin, it looks at `~/.claude/projects` every `streamSeconds`, and reports each session written in the last `idleMinutes`; as it starts it also reports, one by one, those written within `lightsOffHours`, so a runner started again fills the office back in. Such a session stops being reported once it has been quiet longer than `idleMinutes`, or has nothing to report, and is reported again as soon as its transcript moves. A session still on an older version of the plugin runs that version's own data layer, which the runner leaves it to, until a newer version's hooks module connects for it (after a `/reload-plugins`): then the runner reports it for that hooks module, and the older data layer leaves it. Each session's log is `~/.claude/isoplan/logs/<session>.log`.

So that a machine is connected after a restart even for someone who now works only on the floor, install also adds a login item that starts the runner when you log in, for you alone, with no admin rights and no window: it runs `node ~/.claude/isoplan/wake.mjs --login`, which starts the runner as the wake hook does (nothing while the plugin is disabled; the uninstall, below, once it is uninstalled), and the runner's lock leaves one that is already running alone. On Windows it is a value, `Isoplan runner <id>`, under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, which runs Windows Script Host on `~/.claude/isoplan/start-at-login.js` to start node hidden (Task Manager's Startup apps lists it as Microsoft Windows Based Script Host); while Script Host is turned off it isn't added, and the next session's start takes it out. On a Mac it is a LaunchAgent, `~/Library/LaunchAgents/dev.isoplan.runner.<id>.plist`, which runs once at login and is never restarted by launchd, loaded at once with `launchctl bootstrap`; macOS may say in a notification that a background item was added, and lists it in its Login Items settings. On Linux it is `~/.config/autostart/isoplan-runner-<id>.desktop` (under `$XDG_CONFIG_HOME` when that is set). `<id>` names the config folder, so each config folder starts its own runner. Set `startAtLogin` to `false` in `~/.claude/isoplan/runner.json` to stop it: the next session's start, or the next login, takes the item out; set it back to `true` and the next session's start, or the install script, adds it again. While `startAtLogin` is on, the runner doesn't stop when no session on the machine is lit, so the machine stays connected for someone who works only on the floor; with it off, the runner stops about a minute after no session on the machine was used within `lightsOffHours` (24), unless it is running a session driven from the floor.

The link `isoplan://start-runner`, with nothing after it, starts this computer's runner the same way, with no dialog and no window, whatever `startAtLogin` says; a runner that is running is left as it is. It is for the floor's "Restart Isoplan on this machine", and your browser asks before it opens it. It goes to the `isoplan://` link handler (see Install the plugin), which writes what it did to `~/.claude/isoplan/logs/connect.log`; by hand, run `node ~/.claude/isoplan/runner/app/dist/connect.mjs isoplan://start-runner`.

### Driving your sessions from the floor

The runner can run a Claude Code session of yours on this machine that you drive from the floor: start one for a session, send it instructions, read what it did, stop it, or take it back to your terminal. Each such session is one `claude -p --input-format stream-json --output-format stream-json --verbose --permission-mode auto --permission-prompts host --permission-prompt-tool stdio` process (`--permission-mode bypassPermissions` where that is allowed, below), `--session-id <new id>` for a new one and `--resume <id>` after that, hidden, with your own settings, tools, MCP servers and plugins, and saved like any session, so it shows on the floor as your agent. A new session opens in the folder this machine's own record of one of the sessions it joins (Claude Code's transcript of it) names, which must still be there and in a repo the office takes. For a fresh session, the runner tells each office, as it connects and again whenever it changes (it checks every `repoFoldersCheckMinutes`, 5, or `branchRefreshMinutes`, 5, when that is sooner), each repo that office takes where Claude Code sessions ran on this machine: from your sessions of the last `cloneSearchDays` and the ones driven from here, each repo once, by its main checkout, found from any of its worktrees, even one deleted since (the runner remembers which checkout each worktree it saw belongs to, in `~/.claude/isoplan/runner/checkouts.json`), with the branches on its remote, `git ls-remote --heads origin`: never local branches, asked again at most every `branchRefreshMinutes`, with no window or prompt and under `gitTimeoutSeconds`. A remote it can't reach leaves that repo with no branches, logged once. The checkout and each branch are checked for secrets first, at most 100 branches a repo, and no repo the office doesn't take is named. A new session started in one of those folders opens there as a session of its own, with nothing from another session; a folder the runner didn't list, or one no longer in that repo, is refused. Started on one of the branches listed, it opens in the checkout when the checkout is on that branch, and otherwise in a worktree of it: one already on it, or a new one beside the checkout, `<checkout>-branch-<branch>` (with each run of characters other than letters, digits, `.`, `_` and `-` in the name as `-`, and any trailing dots and dashes dropped; a name longer than 24 characters becomes its first 16, `-` and six characters of a hash of the branch), from your local branch of that name as it is, or else fetched from origin. The checkout's own branch is never switched; a branch the runner didn't list is refused. A fresh session can also be kept out of your other tools (New session's Keep out of my other tools, never with Open in Orca; the runner says in its hello that it can): it then works in a clone Isoplan keeps for itself, one per project, `~/.claude/isoplan/clones/<name>`, or `<clonesFolder>/clones/<name>` when `runner.json`'s `clonesFolder` names a folder (the name is the repo's, up to 20 characters, `-` and eight characters of a hash of the project; on Windows its own git config, set as it is cloned, lets git take paths longer than 260 characters, the agent's git too; your repos' config is never changed), made from your checkout's origin as an expert's clone is (only an https, ssh or `host:path` remote; a repo with none, or with a local path or share, is refused with a plain reason and nothing starts), but writable: on origin's default branch as a branch of its own, with the repo's hooks and Git LFS as git has them. One already there is fetched before each use, and never reset or cleaned; one made earlier is used where it is, at the longer name an earlier version gave it or in a folder `clonesFolder` named before. With a branch the session opens in a worktree of that clone beside it, `<clone>-branch-<branch>`; without one, in the clone's own checkout. Your checkout is only read. The agent pushes its work from there, as from any folder. Only the folder is kept out: the conversation is saved under `~/.claude/projects` as any session's, so Orca's session search and Claude Code's resume list show it. Isoplan doesn't delete these clones yet. Isoplan's own folders under `~/.claude/isoplan/`, and the `clones/` and `experts/` of any folder `clonesFolder` has named, are never listed as folders to start in. A fresh session can also open somewhere other than the floor, as a handoff you take can: in a terminal window, as a headless background session, in Orca or in the Claude app. The runner tells each office which of those this machine can open (a terminal on Windows and macOS, Orca and the Claude app only where it finds them, as for takes); it opens the session the same way a take does, in the folder and on the branch above, with your typed task as its first message and nothing from any other session. In Orca, a branch the checkout isn't on gets a worktree Orca makes in the repo's Orca workspace. A task that can't go safely on Claude Code's command line (one starting with `-`, or, for a terminal on Windows, one with quotes, line breaks or a `\` at its end) is written to `task.md` in `~/.claude/isoplan/starts/<session>/` and the first message asks the session to read it; the runner removes such a folder once it is more than 7 days old, as it starts. Such a session isn't the runner's to hold, so `drivenPerProject` and skipping permission prompts don't apply to it: it shows on the floor as any session you open does. A handoff taken as a session driven from the floor gets its worktree as for a terminal, trusted as for headless, and starts reading the brief at once. Only you can act on your sessions: the server checks, and the runner refuses anything not asked by the account it links as, or for a session someone else started. Each instruction runs as one turn; one sent while a turn runs is refused. What the session says, and a short summary of each tool it uses, go to the floor; its full output is sent when you ask for it (a turn's, kept while the runner runs, or the whole session's, from its transcript), cut to 200,000 characters. All of it is checked for secrets first: a reply or output that matches is held back until you release it from the floor, and a tool whose name or summary matches is shown as a tool use with neither. None of it waits in the reply queue: it goes only while the runner's link is up, and after each reconnect the runner tells the server which sessions it holds.

Sessions run in Claude Code's `auto` mode. Whatever still needs your permission comes to the floor as a request saying in plain words what the agent wants to do (the command it would run, the file it would write or change, the address it would open), checked for secrets first like the rest; only you can allow or deny it, and with no answer within `drivenPromptMinutes` (10) it is denied, and the agent is told so. A request still waiting when you stop the session or take it back to your terminal is cancelled. A request isn't queued while the link is down: after each reconnect the runner sends those still waiting again. What Claude Code itself turns down (its permission rules, or its own safety check) never asks, and the floor says it wasn't allowed. If you have chosen to skip permission prompts, a session runs in `bypassPermissions` instead, but only in a project whose office allows it: the office server says which projects those are each time the runner connects and whenever an admin changes it, and until it has said so on the current connection the runner opens nothing that way; a session already running that way goes on until the office's list no longer has its project. A new session asking to skip them where that isn't allowed is refused; a handoff you take, or a session reopened by your instruction or after the runner restarts, runs in `auto` instead, and the floor says why. When an admin turns skipping off for a project, the runner ends that project's sessions that skip prompts at once, mid-turn or not, and your next instruction reopens them with prompts on; a dropped connection alone ends nothing.

While a runner process has a session, it is held, and resuming it in a terminal as well would make two writers: take it back to your terminal from the floor, which closes the process, gives it `drivenCloseSeconds` (30) to finish, ends it after that, and gives you the `claude --resume <id>` command and the folder. Stop stops the reply in progress and keeps the session open (Claude Code's own interrupt); while the agent is idle it does nothing. Close session ends the process at once, mid-turn or not, and your next instruction opens it again; End and remove ends it and removes it, so it is never opened again and its agent leaves the floor. The desktop app's menu offers Close session and End and remove for each session driven from the floor too, and they tell the office the same as the floor's. If the process still hasn't closed after any of these, the session stays held and the floor asks you to try again. A held session with no instruction and no output for `drivenIdleMinutes` (30) is closed, and your next instruction opens it again with `--resume`. At most `drivenPerProject` (4) sessions per project are held on this machine at once; another is refused with the limit. A process that writes nothing within `drivenStartSeconds` (120) of an instruction is ended as stuck, and one that ends by itself is reported; either way the next instruction opens it again. A working turn is never cut short. When the runner restarts, it ends any session process its earlier run left and lists those sessions as not held, to open again on your next instruction. A session the runner is running is on the floor from its first turn: the runner reports it as it reports every session without the plugin (above). Claude Code gives a headless session no title, so as the first instruction of a session started from the floor arrives, the runner asks `namingModel` (Haiku) for a name of 3 to 6 words, once, hidden, with no tools, no settings and no session saved, alongside the turn rather than before it, with the words in `packages/mod/prompts/naming.md`; it is checked for secrets, then shown on the floor and in the desktop app's menu in place of the repo's name. One that doesn't come within `namingTimeoutSeconds` (60) is given up. A handoff taken as such a session keeps its own name.

Every process the runner starts for this is recorded in `~/.claude/isoplan/runner/processes.json`, with each fork answering for a session and each take into the Claude app's first turn while they run, so a separate app can read it. Only the runner writes it, whole, by writing a file beside it and renaming it over. Its format, version 1:

```json
{
  "about": "...",
  "version": 1,
  "runner": 12345,
  "written": "2026-11-06T10:00:00.000Z",
  "processes": [
    {
      "kind": "driven",
      "pid": 23456,
      "spawned": "2026-11-06T09:58:00.000Z",
      "session": "claude-code:3f1c...",
      "folder": "C:\\Users\\you\\app",
      "started": "2026-11-06T09:00:00.000Z",
      "lastActivity": "2026-11-06T09:59:30.000Z",
      "state": "idle",
      "driven": { "room": "...", "project": "github.com/you/app", "office": "wss://...", "owner": "claude:...", "permissions": "auto", "asked": "auto", "transcript": true }
    }
  ]
}
```

`runner` is the pid of the runner's worker that wrote it. `kind` is `driven`, `fork` or `desktop-read`. `pid` is null for a driven session with no process now, which stays listed until it is handed back, Claude Code no longer has its saved conversation, or more than 200 driven sessions are listed (the closed one used least recently goes first). The floor sees such a session gone after the runner next reconnects; a fork or first turn is listed only while it runs. `spawned` is when the runner started that pid; `started`, when Isoplan first started a process for the session. `state` is `working` (a turn is running), `idle` or `closed`. `driven` only on a driven session: its `room`, project, the office it was started through, the account that started it, the permission mode its process runs in or last ran in (`auto` or `bypassPermissions`), the mode its person asked for (`asked`, which it opens in again only where its office allows it; missing from a record an older version wrote), whether a turn has ended in it (so it reopens with `--resume`), and, for a driven take, `addDir` (the handoff's folder with its brief) and `name`. A pid alone doesn't name a process, since the system gives pids out again: the runner counts one as its own only while the pid is alive, the system says it started within 15 seconds of `spawned`, and its command line names the session's id (asked through PowerShell's `Win32_Process` on Windows, `ps` on a Mac or Linux), and ends nothing else.

The runner reads these files. Each file in `~/.claude/isoplan/` is optional:

| File | What |
|---|---|
| `packages/mod/runner.json`, overridden per key by `~/.claude/isoplan/runner.json` | The fork's model (`claudeModel`, Opus by default); the model that names a session started from the floor (`namingModel`, Haiku) and how long it may take (`namingTimeoutSeconds`, 60); the caps on answers per session per hour and per machine per day; the machine's daily token budget, and the weight of each kind of token in it (a cache write costs more than plain input, a cache read far less); the timeouts, including git's for a handoff (`gitTimeoutSeconds`) and a worktree setup script's default (`setupTimeoutMinutes`), how long and in how many turns a take into the Claude app may read the brief (`desktopReadTimeoutMinutes`, `desktopReadMaxTurns`) and how long it may run in all before the app is no longer opened (`desktopTakeBudgetMinutes`), and how long any take may run before it is given up (`takeCapMinutes`); how far back the runner looks for your clone of a repo (`cloneSearchDays`); how many folders down from a session's folder a handoff looks for repos (`repoSearchDepth`, 3); how long an agent waits when it asks the earlier session after a handoff: `askPolls` checks, `askPollSeconds` apart, before it is told to carry on; whether the runner starts when you log in (`startAtLogin`, true); and, for sessions driven from the floor, how long one may sit idle before its process is closed (`drivenIdleMinutes`, 30), how many may be held per project (`drivenPerProject`, 4), how long a process gets to finish when it is closed or taken back (`drivenCloseSeconds`, 30), how long it may take to start on an instruction (`drivenStartSeconds`, 120), how long a permission request waits for your answer from the floor before it is denied (`drivenPromptMinutes`, 10), how often the runner checks again which folders a new session can start in (`repoFoldersCheckMinutes`, 5), and how often, at most, it lists each repo's remote branches again and sends them when they changed (`branchRefreshMinutes`, 5); when to suggest creating an expert, and with which model (`expertCreationSuggestions`, see Expert creation suggestions); and where new clones of Isoplan's own and experts' clones go (`clonesFolder`, empty: under `~/.claude/isoplan/`), an absolute path, read as the runner starts (one that isn't absolute is ignored and the runner log says so): new ones go in its `clones/` and `experts/<name>/read`, and those made earlier stay where they are, since an expert's trunks resume only from their folder. |
| `packages/mod/secret-patterns.json`, plus `~/.claude/isoplan/secret-patterns.json` | The secret scan's patterns, as `{ "patterns": [{ "name", "regex", "flags"? }] }`. Your file adds patterns; it can't remove the plugin's. While your file can't be read, or has a pattern that doesn't compile, every answer, brief and report is held. |
| `packages/mod/prompts/` | What the fork is told: `instructions.md` first, the same every time so the lead's context is reused from cache, then `question.md`, `brief.md`, or `spin-off.md` for a brief written for a spin-off's task. |
| `~/.claude/isoplan/claude-binary.json` | The `claude` binary the fork runs, `{ "path": "..." }`, which install finds and records. Set it by hand if install can't find it; a path set by hand, without `"auto": true`, is kept by later installs. |

The caps are counted on each machine: someone with two machines has two of each.

The runner starts with an environment recorded from the shell that ran the install script, in `~/.claude/isoplan/runner/environment.json`, never with the environment of the session that happened to start it, so a project's settings `env` block can't reach it or its forks. Only the operating system's basics, proxy and certificate settings, and the login and provider variables (`ANTHROPIC_*`, Bedrock, Vertex, `AWS_*`, Google Cloud's, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CONFIG_DIR`) are recorded. You can edit the file; the install script writes it again each time it runs, and uninstall removes it. Without it (installed only through the plugin, or before it existed) the runner uses its starter's environment and says so in its log.

The fork reads no settings files, so a login or proxy that comes from `settings.json` (an `apiKeyHelper`, or an `env` block) doesn't reach it, and its sessions say they can't answer. Claude Code's own login and auth from environment variables (an API key, Bedrock, Vertex) work.

Its log is `~/.claude/isoplan/logs/runner.log`, and its count of answers and tokens for the last day is in `~/.claude/isoplan/runner/ledger.json`.

## Handoffs

Work is handed over from the floor (the session panel's Hand over) or, in the session, with `/isoplan:handover <their name>`. Either way the tracked changes go in a work-in-progress commit made from your current branch without touching your work tree or index, and only that commit is pushed, to `isoplan/handoff/<id>` on the remote your branch pushes to (`branch.<name>.pushRemote`, `remote.pushDefault`, then its upstream): never your current branch, never the default one, and no local branch is made. That keeps a handoff from deploying anything as long as your CI doesn't build `isoplan/handoff/*` branches, so leave them out of it. Tracked files go over, whatever `.gitignore` says; untracked files stay behind and the brief names them, except those `.gitignore` matches, which are never mentioned. From the floor your runner's fork writes the brief and git runs in the background, with no prompts, none of your git hooks, no commit signing, and under `gitTimeoutSeconds`; with the command, your session's own agent writes it. The brief is scanned for secrets before it leaves, and so is everything the push would send: the lines added by each commit the remote doesn't have yet, local commits included. On a match nothing is pushed; the floor says which file holds a possible secret (never the pattern) and names any binary files the scan couldn't read, and you can fix it, or push anyway, which pushes the exact commit that was held. A repo that uses Git LFS is refused, since its files wouldn't go with their pointers.

A handover can carry a new task of its own, which makes it a spin-off: `/isoplan:handover <name>: <the task>` (without a task, it asks whether there is one), or the floor's Hand over with its task filled in. The brief is then written for that task: what it needs from this work, where the code and decisions it touches are, and what to ask this session about, rather than a summary of all of it. The task, at most 4,000 characters, is scanned for secrets with the brief before it leaves. The new session is told to read the task first (it is kept as `task.md` beside the brief), then the brief, and can ask the session it came from questions like any handover. Neither kind stops or pauses the session handing over: it carries on with whatever it was doing.

The receiver takes it with the session panel's Take handoff, which asks how: open it in a terminal, open it as a headless session, open it in the Claude app, or copy a prompt. Every way but the prompt needs Claude Code for the terminal (`claude`) on the receiver's machine, and the runner looks for it before it makes anything, so a machine without it is left without a stray worktree. The runner tells the office whether Claude Code for the terminal is there and signed in, so the floor offers a terminal or a headless session only where it is. Where it isn't, Run it from the floor reads Install Claude to continue: that press installs it with Anthropic's native installer (`irm https://claude.ai/install.ps1 | iex` in PowerShell on Windows, `curl -fsSL https://claude.ai/install.sh | bash` on a Mac), with no window, its progress and any error shown on the floor. Claude Code for the terminal keeps its own sign-in, apart from the Claude app's, so a fresh install asks you to sign in: that press runs `claude auth login`, which opens the sign-in in your browser, and the take carries on once it is done. The first three have their runner find their clone (the folder, most recently used first, of one of their Claude Code sessions whose fetch or push URL is the handoff's remote, never one of Isoplan's own under `~/.claude/isoplan/`, such as an expert's), add a worktree beside it, `<clone>-handoff-<id>`, on the handoff's branch, with the repo's git hooks off, run the repo's setup script, then start Claude Code there, told to read the brief, which is kept in `~/.claude/isoplan/handoffs/<id>/`. In a terminal is the only path that opens a window (on Windows through `start`, a Windows Terminal tab where that is the default; on a Mac, Terminal), and only when that is what was asked. Headless starts a background session, `claude --bg`, with no window, which you open with `claude attach` and which `claude agents` lists; Claude Code runs one only in a folder it trusts, so this records trust for that worktree alone in `.claude.json`, and the floor says so before you choose it: the worktree's Claude settings, hooks and setup scripts will run. Open in the Claude app is offered where the runner found Claude Code for the terminal, version 2.1.285 or newer, signed in with a Claude subscription (not an API key, Bedrock, Vertex or Foundry), on a Mac or Windows x64; the runner checks as it starts and every hour, and the office learns it when the runner's link next connects. The Claude app runs its own Claude Code and doesn't put `claude` on your PATH, so install Claude Code for the terminal too. The take checks all of that again before it makes anything, and refuses when `claude auth status` doesn't answer. Then it trusts the worktree as for headless, runs the first turn hidden and to its end (`claude -p --permission-mode default`, as a saved session, so a `defaultMode` in the branch's settings can't loosen it and nothing that would ask is allowed, in at most `desktopReadMaxTurns` (10) turns and `desktopReadTimeoutMinutes` (5)), and opens that same session in the Claude app with `claude --desktop --resume <id>`, so the app shows it ready to continue, not a prompt to send. A first turn that fails has its unfinished session deleted, and the floor says so. The app isn't opened if the take was cancelled or timed out on the floor meanwhile, or ran past `desktopTakeBudgetMinutes` (15, under the office's own take timeout); if the app itself doesn't open, the session is still taken and the floor says to open it from the app's session list or with `claude --desktop --resume <id>`. With `CLAUDE_CONFIG_DIR` set, the session is kept there, which the Claude app may not read. The first turn's tokens aren't counted in the runner's daily budget. Any take still running after `takeCapMinutes` (45) is given up, and the floor is told. Where Orca is installed (its CLI on Windows or a Mac), the floor offers Open in Orca first, for a handoff of one repo: the runner adds your clone to Orca if it isn't there, has Orca make the worktree on the handoff's branch in the repo's Orca workspace (with Orca's own setup skipped; a worktree made for the handoff before, a local branch of that name, or a clone with `core.hooksPath` set gets the worktree described above instead), runs the setup script, trusts the worktree as for headless, and opens Claude Code there in an Orca terminal, in front, in your running Orca window. A worktree from an earlier take moves to the branch as handed over now, unless it holds work of yours that isn't in it (changes to tracked files, or a commit that is neither in the new tip nor one this machine took of the handoff before): then it is left alone and the take says why. A failed setup script doesn't stop the session opening; any step that fails is shown in the session with the end of its output, scanned for secrets. The copied prompt is `/isoplan:take <code>` for a session you already have: it checks the branch out in that session's folder, refusing a folder with uncommitted changes, and moving a local branch of that name to the new tip, never over commits of yours, and loads the brief. No setup script runs there, since you or your harness set that folder up; when the repo has one, the agent is told it hasn't run.

A session can work in a folder that holds several repos, cloned inside a parent repo that usually ignores them, or inside a plain folder that isn't a repo at all. A handoff finds every repo under the session's folder, up to `repoSearchDepth` folders down, whether or not the parent ignores them. Folders whose names start with a dot, `node_modules` and links aren't looked in; any of those that is a repo itself, a repo one level too deep, and a folder that couldn't be read are named in the brief as left out. A session in your home folder or at a drive's root can't hand over: that is too wide a folder to look through. The parent always goes; a repo under it goes only when it has work its remote's default branch hasn't (changes to tracked files, or commits that aren't on that branch; with no default branch known, commits on none of the remote's branches), each by every rule above on its own: its own `.gitignore`, remote and default branch, its own branch, and the same secret scan. Repos that push to one remote get a branch each there, `isoplan/handoff/<id>--<path>` after the first. The brief's note lists every repo handed over and its branch, so the floor shows them in the meeting. Every file in every repo whose added lines match is held, named by its path in the folder, and one release pushes all of those exact commits. A repo under the folder with work but no commit or no remote, or one git can't read, is left out and named in the brief (a clean one with no remote isn't mentioned, and the folder's own repo with no remote refuses the handoff, as above); in a plain folder, the files outside every repo are named as not handed over; git submodules aren't handed over either, and are named. If a push fails after some repos' branches went, the failure says which went, and handing it over again with the same id pushes the rest. Taking it checks out each repo at its path after the setup script, so the script sees only the repos it clones itself: one there already, say one the script cloned on main, is fetched and switched by the shortcut's rules, and one that isn't there is cloned from its remote, only when that is an https, ssh or `host:path` remote (never a local path, `file://` or a `\server` share), with Git LFS's download off. A path into a `.git` folder, in any spelling Windows reads as one, or out through a link, is refused. One that fails is shown in the session by its path, and the session still opens. A handoff from a plain folder has no worktree to make: the floor makes a plain folder beside yours (`<folder>-handoff-<id>`, where your folder is the most recent session folder holding one of its repos) and clones its repos into it, with no setup script, since no repo there holds `isoplan.json`. The shortcut does the same in the session's own folder; run from inside one of the handoff's repos, it works from the folder above it.

With several office servers, `/isoplan:handover` hands over in the one office that takes the session's repo; when more than one does, it asks you which, and passes `--office <label>`. `/isoplan:take <code> --office <office>` (a label, a server's address or its host) asks that office alone which work the code takes over; if it can't say (it can't be reached, this machine isn't paired with it, or it doesn't know the code), the take stops there and names it. Without `--office`, each office in `config.json`'s order is asked, with this machine's pairing token where it is paired, and the first that knows the code decides: if this machine's copy of its list doesn't take the code's repo, the take is refused rather than tried in the next office. A take code is single-use and works only for the person it was made for, so an office that doesn't know it learns nothing it can use. Only an office that signs people in is ever named as needing pairing.

With sign-in on, `/isoplan:handover` and `/isoplan:take` send this machine's pairing token like a session's link does, renewing it when it has run out. They never pair the machine themselves: if it isn't paired, or its pairing has ended, they say so and point at the **Pair this machine** link a session shows.

The setup script is set once per repo, in `isoplan.json` at its top, committed:

```json
{
  "worktreeSetup": {
    "about": "Runs in each new worktree Isoplan makes when someone takes a handoff from the floor.",
    "command": "pnpm install",
    "timeoutMinutes": 15
  }
}
```

`command` is one command, or `{ "windows": "...", "mac": "..." }`. It runs with the system shell (cmd.exe on Windows, /bin/sh on a Mac), hidden, in the new worktree, with `ISOPLAN_HANDOFF_ID` and `ISOPLAN_HANDOFF_BRANCH` set. It is read only from the remote's default branch, as your clone fetches it, never from the handoff's branch or whatever your clone has checked out; when the default branch can't be told, setup is skipped and the session says why.

## Asking the earlier session

Once you have taken a handoff, your session's agent gets the plugin's `ask_earlier_session` tool (`ask_room` in older plugins) and can ask the earlier session a question, without you typing anything; sessions that took no handoff don't have the tool. Only a taken handoff gives that right, only for that work, and the person who handed it over can turn it off on the floor, and on again. With rights in more than one office, the agent asks in the office the session took its handoff from, else in the first of them in `config.json`'s order. The question goes through the office server to their runner on the machine with the original session, whose fork of the lead answers from the session's own context, within the caps in their `runner.json`, and the answer is checked for secrets on their machine before it leaves. Your agent is given the answer marked as another person's session, quoted, as information rather than instructions. Every question and answer shows under the session on the floor, and the server keeps them for its retention period; the office's `asks.json` caps how many questions one person may have waiting and ask in a day.

Your agent is never held up for long: when their machine is off, their runner is away, a cap is reached or the answer is held, it checks `askPolls` times, `askPollSeconds` apart, then is told to carry on. The question stays queued and is asked again when their runner is back; an answer that comes later reaches your agent as a note on one of its next tool results. The tool asks through the machine's runner, and only for a session whose hooks module is connected to it; a question that looks like it holds a secret isn't sent. When the office signs people in, it asks with this machine's pairing, as the session reports; on a machine that isn't paired, or whose pairing has ended, your agent is told so and carries on.

## Experts

An expert is a read-only agent on your machine that knows one subject in one repo well, and answers other agents' questions about it, from any machine in the office. It never writes code or acts. Its trunk is a Claude Code session the runner grounds once in the subject, in a checkout of the repo's default branch of its own, and never compacts; each question runs on a fork of the trunk, which leaves no transcript, and the answer cites the files it read, at a commit. You host it, so your Claude subscription pays for its answers, within the caps below. Claude Code's auto memory is off in every expert process, and none of your Claude Code hooks runs in one, nor in its proof's judge. Its trunks and forks are never reported to the floor; the office's floor shows the expert itself at a desk, with its state, and each question to it as a meeting, without the question's words.

### The expert file

You start an expert by writing `~/.claude/isoplan/experts/<name>.json`, the one file of it you edit:

```json
{
  "version": 1,
  "name": "what-leaves-a-machine",
  "repo": "C:/Users/adamr/Projects/Isoplan/isoplan-app",
  "subject": "What session text may leave a person's machine and under what rules (ADR 0004), and how one session asks another (asks.ts). Ask before you add anything that sends data off a machine or stores session text on the office server.",
  "model": "sonnet",
  "promoteAtTokens": 45000,
  "forkTimeLimitMinutes": 5,
  "caps": { "perAskerPerDay": 30, "openPerAsker": 3, "tokenBudgetPerDay": 2000000 },
  "proof": {
    "question": "If a session runs in a repo the office doesn't take, what does the plugin send to the office server about it?",
    "answer": "Nothing at all, not even its hello or its repo's id."
  }
}
```

| Field | Required | What |
|---|---|---|
| `version` | yes | `1`. A file written for a newer runner is refused. |
| `name` | yes | Lowercase letters, digits and dashes, at most 63, the same as the file's name. Agents ask it by this name, which is unique in the office: the first host to list a name keeps it. |
| `repo` | yes | An absolute path to a git checkout whose `origin` remote is a repo the office takes, at an https, ssh or host:path URL. |
| `subject` | yes | Up to 1,000 characters: what to ask it about, and before which changes. Every agent in the office sees it, so it is checked for secrets before it leaves. |
| `model` | yes | The model it grounds and answers with. |
| `promoteAtTokens` | yes | The size of its junior's context at which a new generation takes over (below). It must leave at least 100,000 tokens before the model's compaction point. |
| `forkTimeLimitMinutes` | no | 5: how long one question may take. |
| `groundingTimeLimitMinutes` | no | 15: how long a grounding may take. |
| `fetchSeconds` | no | 60: how often, at most, it fetches the default branch before a question; 0 fetches before every one. |
| `maxForks` | no | 3: how many questions it answers at once. |
| `caps` | no | `perAskerPerDay` 30, `openPerAsker` 3, `tokenBudgetPerDay` 2,000,000 (in `runner.json`'s weighted token units). |
| `proof` | yes | A question with its expected answer, asked after every grounding. |
| `window` | no | The model's context window, when the runner's table doesn't know it (at least 100,000). |
| `areas` | no | Globs of the files it covers, kept for later and unused now. |

Every number is a whole number of at least 1, except `fetchSeconds` and `window`. A field the runner doesn't know is logged, not fatal; a file that doesn't parse is logged, to `runner.log` and the expert's health log, with the field and the reason, and that expert doesn't start (one already running keeps running). The runner looks at the folder every few seconds. A change to `subject`, `model`, `proof` or `window` grounds a new generation in the background while the old one keeps answering; a new `repo` starts the expert over, removing its old clone first. Other fields apply at once. Removing the file stops the expert and keeps its folder; a file counts as removed only once two looks in a row miss it, since an editor that saves by deleting and writing again leaves it missing for a moment.

### Where things are

Its state (the ids of its trunks, and which files each read at which commit) and its caps ledger are in `~/.claude/isoplan/experts/<name>/`. Its health log is `~/.claude/isoplan/logs/expert-<name>.log`: each grounding, proof question, promotion, question (by id, with its time and cost), cap reached and error. Its own clone of your `repo`'s origin is there too, `read/`, detached at the default branch, where every trunk and fork runs; or in `<clonesFolder>/experts/<name>/read` when `runner.json`'s `clonesFolder` named a folder as it was first made. It stays where it was made, since its trunks resume only from there. On Windows git takes paths longer than 260 characters in it, set in its own config as it is cloned. It is a clone, not a worktree of your checkout, so it doesn't show under your repo in Orca or `git worktree list`, and takes and New session never use it as your clone. That hides the folder, not the conversations: its trunks are Claude Code sessions saved under `~/.claude/projects`, so Orca's session search and Claude Code's resume list show them (see below for why you shouldn't resume one). The clone borrows your checkout's objects while it is made, so little comes over the network. Your checkout is only read, for its origin's URL and default branch. A `read/` that isn't a clone of its own, such as a worktree an earlier plugin made, is left as it is and the expert doesn't start until you remove it.

### Generations and the proof question

A generation is one trunk, from its grounding to its retirement. After each grounding, a fork answers the proof question, and a model with no tools (`expertJudgeModel` in `runner.json`, Haiku) compares its answer with yours; both answers and the verdict go to the health log. A generation that passes becomes the junior and answers questions. One that fails takes none: the generation before it keeps answering, and with none, questions fail with `EXPERT_FORK_FAILED`. A failed grounding, proof or promotion is tried again on its own, 10, 30 and 90 minutes later, at most three times, and then not until you change the file or the runner restarts; one that would fail every time (`promoteAtTokens` against the model's window, or no room for notes) isn't tried again until you change the file. A judge that crashes or runs out of time fails the generation, but isn't logged as a failed proof. A fork that asked the senior or explored adds what it found to the junior's trunk as a learned note, so the trunk grows. Once it reaches `promoteAtTokens`, a new generation grounds; when it passes, it becomes the junior, the old junior becomes its senior, which the junior asks before exploring, and the one before that retires. A generation that compacts fails, and a new one grounds. A retired or failed generation's trunk transcript, the folder beside it and its index are deleted (at promotion, retirement and a repo change); its record stays in `state.json`. Don't resume a trunk yourself: every later fork would inherit what you add, so the runner checks each trunk before and after each learned note and right before forking a junior, a trunk with turns the runner didn't add is no longer used, and a junior's is replaced by a new generation; a question that meets one is refused as unavailable, and the office asks it again. So is a question that comes while a fork's changes to the clone wait for a grounding to finish before they are reset. While it hosts an expert, the runner stays up, lit or not, so its experts can answer.

### Asking

Once the office tells a session which experts it may ask, its agent gets the `ask_expert` tool, which lists them with their subjects; a session in an office with no experts, or on an older plugin, doesn't have it. The agent sets `blocking` itself: true only when it can do nothing else until the answer comes. A blocking call waits up to `expertWaitSeconds` (10, in `runner.json`) and then tells the agent to explore meanwhile; any other returns once the office has the question. An answer that comes later reaches the agent as a note on one of its next tool results, as ask_earlier_session's do. The runner tells the office it has an answer only once it has reached the agent, so one the agent never got (its call timed out, say) comes again as a note. The question goes from the runner on the asker's machine, which checks it for secrets first, to the office server, and on to the runner hosting the expert. While that machine is away, the question waits and is asked again when it reconnects, or is dropped after `maxAttempts` tries or `maxAgeHours`, with a note saying why.

### Caps

The host's caps are the expert file's: questions per asking session per day, open questions per asking session, and the expert's daily token budget, counted in its own ledger, apart from the caps in `runner.json`. Raise them in the expert file. The office's are in its `asks.json`, raised by an admin: `openPerAskerPerRoom` is also how many questions one person may have waiting for one expert, and `perAskerPerDay` how many expert questions one person may ask in a day, counted apart from questions to earlier sessions.

### What leaves the machine

From the host: each expert's name, subject, repo, state and whether it has a senior, only to an office that takes the repo, at most `MAX_EXPERTS` of them (the runner's log names any left out); its answers, each checked for secrets first, and an answer that matches is refused at once, never held; and, to an office that says it reads it, a notice with no text, under the question's request, when the junior first asks its senior, so the floor shows the senior join the meeting. When git fails to read an expert's remote for a reason other than there being none, the runner keeps the listing it last sent. The trunks, forks and learned notes stay on the machine. From the asker: the question, checked for secrets first. The office server holds a question and its answer only while it is in flight: their words are deleted once the asker has seen its end, or after twice `maxAgeHours` when it never does, and a record without words stays a day, for the daily cap.

### What ask_expert's replies mean

Every reply names the expert and the question's id, which the host's health log uses too, and ends with a code:

| Code | What happened | Fix |
|---|---|---|
| `EXPERT_RUNNER_UNREACHABLE` | The runner on the asker's machine, or its way to the office, can't be reached; nothing was sent. | Check that the runner is up and the machine is paired, and ask again. |
| `EXPERT_REFUSED` | The office server refused the question, for the reason the reply gives (the session isn't held yet after a reconnect, say); it wasn't asked. | Do what the reason says, then ask again. |
| `EXPERT_UNKNOWN` | No expert of that name in the session's office. | Ask one of the names the reply lists. |
| `EXPERT_CAP` | A cap was reached, the office's or the host's; the reply says which, and when it frees. | Wait, or raise it: the office's in `asks.json` (an admin), the host's in the expert file (its owner). |
| `EXPERT_QUESTION_HELD` | The question looked like it held a secret, so it wasn't sent. | Ask again without it. |
| `EXPERT_PLUGIN_OLD` | This machine's plugin, or the host's, is from before experts. | Update the Isoplan plugin on the machine the reply names. |
| `EXPERT_QUEUED` | The host's machine isn't connected; the question waits. | Nothing: the answer, or why it was dropped, comes as a note. |
| `EXPERT_STARTING` | The expert is grounding a new generation. | Nothing: the answer comes as a note. |
| `EXPERT_FORK_FAILED` | The fork failed, timed out or ran out of room, the expert hasn't passed its proof question, its answer looked like it held a secret, or the office server couldn't read the host's reply; the reply gives the cause. | The host looks at the health log; the agent explores instead. |
| `EXPERT_DROPPED` | The question was dropped: too many tries, too old, the host gone too long, the expert or its repo gone, or the asker's repo and the expert's no longer in one office. | Ask again if it still matters. |

An answer that matches the host's secret check is refused at once with `EXPERT_FORK_FAILED`, and the asker explores instead: an expert runs on its own, so nothing is held for a person to release. The match is logged, so it can be looked into: a `question id=… outcome=secret` line in `~/.claude/isoplan/logs/expert-<name>.log`, and the pattern's name, never the answer, in the runner's log.

### Expert creation suggestions

You don't have to write an expert file yourself: the runner suggests creating an expert where a session would have been helped by one. For each session it reports, it counts, per folder of the repo, the Read, Grep and Glob calls of the session and its subagents (a search at the repo root, as most are, in the deepest folder holding all its results), what their results took (characters / 4, as tokens), the time from each call to its result, and your corrections while the agent worked there: an interruption or a tool call you turned down, and, only when you turn the correction check on (`correctionCheck`, off by default, since each check spends your own tokens), a message that a quick `claude -p` check (Haiku, no tools, none of your hooks) reads as telling the agent it was wrong; it runs on your own Claude account, so what it is given goes only to your account, never to the office, and its word on each message is kept in `expert-creation-suggestions.json`, so a runner started again never checks a message twice. A folder passes when its reads and searches took `contextShare` (0.15) of the session's context window or `tokens` (30,000), or took `minutes` (10), or had `corrections` (2); the deepest folder that passes is suggested, once per session and folder. Never one you dismissed, and never one an expert on this machine covers by its `areas` (the protocol's `areaCovers`, the office's rule too); the office checks other machines' experts. The settings are `expertCreationSuggestions` in `runner.json`, overridden key by key in `~/.claude/isoplan/runner.json`, and include the model that drafts and checks (`draftModel`), whether the correction check runs (`correctionCheck`, false), how many correction checks may run an hour (`checksPerHour`, 20), how long each may take (`timeoutSeconds`, 60), how long the folders already suggested to each session, and the suggestions, are remembered (`rememberDays`, 30), and the `promoteAtTokens` an expert created from a suggestion gets (100,000). A folder whose draft couldn't be made is tried again for that session an hour later, a restart included, and so is the folder of a suggestion every office it went to refused, an hour after the last refusal.

The runner drafts the expert with the same model, through `claude -p` on your own Claude account, so what the draft is given goes only to your account, never to the office: a key such as `pairing` (shown as "Pairing Expert"), a subject, and a proof question with its answer, from the names of the folder's files, the start of the first few of them (the proof is taken from those) and what the session said there. The whole draft, its folder included, is checked for secrets before any of it leaves; a match means no suggestion, and the runner's log says so. Nothing is suggested on a session until the office it reports to has sent your dismissals. The suggestion goes to each office that takes the repo (for a folder of another repo the session worked in, only to an office that holds that repo), and the session's status line links to its review on the floor once that office has kept it: an office ends a suggestion it won't keep at once, so one it hasn't ended within 5 seconds is open. Each suggestion open in an office goes to it again on each new connection, so an end lost with a dropped connection still comes, and a suggestion the office has no record of is refused. Whoever creates the expert picks one of their own computers; that computer's runner finds its checkout of the repo (as New session does), or, with none, clones the repo for the expert alone into Isoplan's own hidden folder (`~/.claude/isoplan/clones/`, or `clonesFolder`'s), never into your folders, from `https://<repo id>.git`; a repo with no remote, or a clone git refuses, fails the creation with git's reason. It writes `~/.claude/isoplan/experts/<key>.json`, its `repo` the checkout or that clone, and reports each step to the floor until the expert is ready, when the session that showed the need gets a note. A creation that fails after that removes the file, so the computer stops hosting the expert, and creating it again with the same key starts fresh. Which sessions and folders were suggested, the folders waiting to be tried again, the suggestions, and the expert creations under way and done (each with its last state for `rememberDays` once it is ready or failed, sent again on each new connection, so a ready lost with a dropped connection still reaches the office, and creating the expert from the same suggestion with the same key again answers ready) are kept in `~/.claude/isoplan/runner/expert-creation-suggestions.json`, so a runner started again goes on reporting a creation; one that can't be read is logged and moved aside as `expert-creation-suggestions.json.unreadable-<time>`, and suggesting starts again from nothing; a session's open suggestions are also in `~/.claude/isoplan/expert-creation-suggestions/<session>.json`, for `/isoplan:review-expert-suggestion`.

```json
"expertCreationSuggestions": {
  "contextShare": 0.15, "tokens": 30000, "minutes": 10, "corrections": 2,
  "rememberDays": 30, "draftModel": "haiku",
  "promoteAtTokens": 100000, "correctionCheck": false, "checksPerHour": 20, "timeoutSeconds": 60
}
```

The office decides the rest in its `asks.json`: how many sessions (`officeWideSuggestionMinimumSessions`) searching one folder within how many days (`officeWideSuggestionWindowDays`) make an office-wide suggestion, the model the review proposes (`suggestedExpertDefaultModel`), and how long "Not now" lasts (`dismissedSuggestionSnoozeDays`).

In Claude Code, while a suggestion is open, Isoplan's status line carries `A Parser Expert could help · review: <link>` after the office's part, and the transcript gets one line saying what the session spent on the folder, with the same link. The link opens the review on the floor, where you can change the draft, pick which of your own computers runs the expert, and press Make expert; `/isoplan:review-expert-suggestion` opens the same review in your browser. The link goes once the expert is made or the suggestion is dismissed or expired; made or dismissed in one office, it is withdrawn from the others. When the expert is ready, the agent is told on its next tool result to ask it (`ask_expert`, with the expert's key as `expert`) before searching that folder again.

What leaves the machine, under ADR 0004's case for an expert creation suggestion's draft: the draft (key, subject, folder and proof question with its answer), after the secret check, with the suggestion's id, session, repo and the numbers that passed their thresholds. The office deletes it once the expert is made, the suggestion is dismissed, or after 7 days. The folder's files, the start of a few of them and what the session said there, which the draft is written from, go only to your own Claude account, for the draft, never to the office.

## Answering from the floor

When an agent asks you something (`AskUserQuestion`), the question shows in the terminal and on the floor at once, and the first answer wins: answer it in the agent's details on the floor and the terminal's dialog closes, and the agent gets your answers as if you had picked them in the terminal. Only you can answer your own sessions' questions there, and only you, and an admin with Overview on, can read them; everyone else sees that your agent is waiting on you. The floor offers a question only while the plugin is waiting for it in that session, so one in a session the runner reports, without the plugin, or asked before the plugin loaded, is read-only there: answer it in its terminal. A question is secret-checked before it leaves, as reports are: one that matches, and every one while the patterns can't be read, goes as a placeholder and is answered in the terminal. A report the secret check held is released from the same place.

You can also carry on a session you opened yourself, in a terminal, Orca or anywhere else, from the floor: a message you send it there goes into the session as your own next turn, with Claude Code's `$.prompt.submit` (Claude Code 2.1.312 or newer; the floor offers it only for a session that can take it). One sent while the agent is working waits for its turn to end, and several go in the order you sent them. It never touches what you have typed in the terminal's prompt box, and no window comes to the front. Only you can send your sessions messages: the server checks, and the plugin refuses one from anyone else. A session the runner reports, without the plugin, one in an older Claude Code, and one that has ended or gone on as a new one (a `/clear`) can't take it. When a message is refused before it is sent, the floor says why. One the floor already showed as waiting its turn that then can't go in isn't reported again, so check the terminal. A permission prompt the turn runs into is answered in the terminal.

This rests on how Claude Code's dialog behaves while a hook waits, which `scripts/probe-ask-dialog.mjs` checks in a hidden terminal with a throwaway config folder (it needs `node-pty`; see its header): the dialog shows while the hook waits, an answer the hook gives closes it and is taken as the question's answer, and a multi-select answer is the picked labels joined with ", ", with any words typed under "Type something" after them. Run it after a Claude Code update.

## What leaves your machine

Nothing at all of a session in a repo the office doesn't take. An admin lists the company's repos on the floor (Repos), and the plugin reads that list from the office server (`/data-layer/repos`, beside the `server` address: every approved repo's id, with this machine's pairing token when the office signs people in) every `approvedRefreshMinutes` (5), whenever its link drops, and before every reconnect, keeping a copy in `~/.claude/isoplan/offices/<id>/approved.json`, one per server. With several servers, each server's list decides for that server alone. A copy the server hasn't confirmed for `approvedMaxAgeMinutes` (15) approves nothing. A session in any other repo opens no connection and sends nothing, not even a hello or its repo's id; the status line says "this repo isn't in the office", and the plugin's log says why. A session the plugin doesn't run in, which the runner reports, is then left alone, and reported again once this machine's copy of the list takes its repo. Once an admin adds the repo, its sessions connect at the next check, or soon after `/isoplan:repos`, which asks every office at once and keeps its answer in the same copy: each running session and the runner take it at their next pass (within a minute), and a session the runner isn't reporting at its next message; once one is taken out, their links close. With no list (the server can't be reached and there is no fresh copy, or the server is too old to give one), nothing is sent. The handoff and ask-the-earlier-session commands go by the same copy; taking a handoff with its code looks up the work's repo by the code and says hello as that, so the folder you take it in is never named. What isn't a session's carries no repo id: pairing sends this machine's name, its random id and the Claude account's label, and the runner's link says hello with the account and the machine's name, and, while it hosts experts, lists each one's name, subject, project, state and whether it has a senior, only for repos the office takes and never for a repo with no remote; the runner answers only for sessions in repos the office takes.

For a repo the office takes, by default only facts: which sessions and agents are running and what kind of work each is doing, in which repository and branch, which files they touched, when they wait, and, per folder, how much they read and searched there (counts, tokens, minutes and corrections, never what they read or searched for). Session-derived text leaves only in named cases, each kept by the server for a set period and then deleted: an agent's final report, questions an agent asks its owner, the questions, answers and briefs of work that was handed over, questions asked of an expert and its answers, which the server holds only while they are in flight (see Experts), and an expert creation suggestion's draft: its key, subject, folder and proof question with its answer, checked for secrets first (see Expert creation suggestions). A report, and a question an agent asks you, is checked for secrets on your machine before it is sent, as answers, briefs and expert questions are. A report that matches stays a placeholder, a note saying it is held, until you release it from the floor; with several offices, a release on one office's floor lets it out to that office alone, and the others keep the placeholder until it is released on theirs. A question that matches is answered in the terminal. A pattern you add after a report went out can't recall it.

An agent often works in more than one repo: editing files with Edit or Write, or with shell commands (Bash, zsh, PowerShell or cmd) that cd somewhere else or point a tool at another folder (`git -C`, `npm --prefix`, `pnpm -C`, `make -C`). The plugin works out which repo each file and command is in, but a file, command or subagent's worktree in a repo other than the session's own leaves your machine only when the office it reports to holds that repo, and only to an office server that says it reads them: when it lets a session in, the server names the office's repos (and, of repos with no remote, only this machine's). Everything else stays on the machine, as before. A session in a plain folder above several repos (a workspace, holding between one and `workspaceRepos` repos, never your home folder or one above it) is reported like a repo with no remote: its project is the folder's path on this machine, lower-cased on Windows and macOS. It reports once the office takes any repo inside it, as the first of those by name (its session stands in that repo's district), and sends only its work inside repos the office takes, each named by its repo; its own files, outside every repo, stay on the machine, and the folder's own path is never sent. A hand-over from it takes only the repos the office takes, and names the others to you alone.

## Release

The plugin's version in `packages/mod/.claude-plugin/plugin.json` is the release gate: commits on main reach nobody until it changes. Once a change has run on the dogfooding machine, release it: bump that `version` (and `packages/mod/package.json`'s to match, which Claude Code doesn't read), rebuild `dist/`, and merge to main. Every install picks it up within `updateCheckHours`, through the plugin's own check or Claude Code's auto-update (see Updates). Set the version only in `plugin.json`, never in the plugin's entry in `.claude-plugin/marketplace.json` too: Claude Code takes `plugin.json`'s without a warning, so a second copy only goes stale. Rebuild `dist/` with every change to `src/`, since the plugin runs it as committed.

To release the protocol, set its version in `packages/protocol/package.json`, and publish a GitHub release for the tag `protocol-v<version>`, such as `protocol-v0.3.0`. That runs `.github/workflows/publish-protocol.yml`, which fails unless the tag matches the package's version, waits for approval if the `npm-publish` environment asks for it, and publishes `@isoplan/protocol` to npm unless that version is there already. It uses npm trusted publishing, so no npm token is stored in the repository, and each version carries a provenance statement. Releases for other tags publish nothing.

Earlier history of both packages is in Isoplan's private repository.
