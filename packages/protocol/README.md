# @isoplan/protocol

The wire protocol between [Isoplan](https://github.com/isoplan-app/isoplan-plugin)'s Claude Code plugin and an office server: the facts a session reports, the messages each side sends, and [zod](https://zod.dev) schemas that check them.

```
npm install @isoplan/protocol
```

ES module only, with TypeScript types. Depends on zod 4.

## What is in it

- **Facts** (`FactsSchema` and its parts: `SessionFactSchema`, `AgentFactSchema`, `FileFactSchema`, `WaitFactSchema`, `ReportFactSchema`, `QuestionFactSchema`, `WorkflowFactSchema`): what one session reports, the shape a data layer sends and a server stores. A Claude Code workflow run is a `WorkflowFact`, and each of its agents an `AgentFact` whose `workflow` names the run, its phase and its label; their text is bounded by exported `MAX_WORKFLOW_*` constants. From 0.15.1 a data layer keeps a report's text within `MAX_REPORT_LENGTH`: it keeps the start of a longer one, cuts it to fit, ends it in "…" and marks it `cut`. An older data layer sends the whole report, so a longer text still parses, and an older side ignores `cut`.
- **Messages**: `DataLayerMessageSchema` for what a data layer or runner sends (hellos, full facts, changes, replies, refusals, and the hand-over, take and taken steps of a handoff, and ask-room, ask-check and asked-ack for asking a handed-over room a question), and `OfficeServerMessageSchema` for what a server sends back (repair, conflict, error, request, release, handoff, asked, where a question stands, and ask-rights, whether a session may ask). Each message type has its own schema and type as well, such as `HelloMessage` or `RequestMessage`.
- **Driven sessions** (0.5.0): a session the runner runs on its person's machine, which they drive from the floor. The server sends `drive` (start, instruct, stop, hand-back, output, answer a permission prompt, release withheld text), each naming who acts, and `drive-policy`, where skipping permission prompts is allowed. The runner sends `driven` (started, turn-started, tool, reply, turn-ended, error, output, prompt, prompt-ended, held, released, handed-back, refused, holding, its sessions, once per connection, and folders, where a new session can start for each repo the office takes, with that and whenever it changes), only while its link is up, and only once the connection's first `drive-policy` has come, so a server from before driven sessions, which sends none, is never sent one. A start names a room, or a folder from the runner's last `folders` and no room, for a fresh session in a room of its own (`room:<session>`). From 0.9.0 a runner lists each repo once, by its main checkout, with `branches`, the branches on its remote (absent from an older runner, or one that couldn't reach the remote), and sends `folders` unasked every few minutes when they changed; a start in a folder may name one of those as `branch`, which opens in a git worktree of it beside the checkout unless the checkout is on it already. From 0.10.0 such a start may say where it opens, `mode`, as a take does (`terminal`, `headless`, `orca`, `desktop`, or `driven`, the default), with its first instruction; a runner says the places it can open in its hello's `starts`, and is sent a `mode` only then, and answers a start that opened elsewhere `opened`. A runner that drives sessions says `drive` in its hello, and can take a handoff as one (mode `driven`). Their text, ids, rooms, tool names, a start's room sessions, the `holding` list and the folders listed are bounded by exported `MAX_*` constants, which a runner keeps its messages within; the acting person (`by`) and project ids aren't bounded, as they aren't anywhere else in the protocol.
- **Claude Code on the machine** (0.7.0): a runner's hello says `claude`, whether Claude Code for the terminal is there and signed in (`ready`, `signed-out`, `missing`), and `driven` `claude` says it again whenever it changes. The server can send such a runner `install-claude`, which runs Anthropic's native installer with no window, and `sign-in-claude`, which runs `claude auth login`; the runner answers each with `claude` messages under the request's id, with the installer's progress, the sign-in link, or why it failed.
- **Spin-offs** (0.10.0): a handoff may carry a `task` of its own, at most `MAX_TASK_LENGTH` characters, which makes it a spin-off: the brief is written for that task, and the new session starts on it. The task rides in the handoff (`hand-over` and `handoff`), in `hand-over-check`, and in the floor's `write-brief` request; a `write-brief` reply doesn't repeat it. An older side ignores it.
- **Questions as Claude Code asks them** (0.11.0): a question's options may carry a `preview`, and the floor's `owner-answer` request may carry `annotations`, keyed by question text: the owner's `notes` on each answer and the `preview` of the option chosen. A question fact may say `asMessage`: the hooks module didn't see it asked, so the plugin answers it by stopping the turn and submitting the answers as the owner's own message. A session fact says `hooks` when Isoplan's hooks module runs inside it. An older side ignores them. From 0.11.1 an `owner-answer` may say `chat` instead: the owner chose "Chat about this", and `answers` is empty.
- **Stop the reply, end and remove** (0.12.0): `drive` `interrupt` stops the reply in progress and keeps the session open; its turn ends `turn-ended` `stopped`, and with no turn running it does nothing. `stop` may say `remove: true`: the runner also forgets the session, never to open it again, and answers `released` with the new `why` `removed`, which it also sends when its person ends and removes the session on the machine itself. A runner from before 0.12.0 drops `interrupt` and ignores `remove`; a server from before it drops a `released` `removed`.
- **Experts** (0.13.0): read-only agents a machine's runner hosts, each grounded in one repo, which a session in an office that holds that repo may ask from any machine, through the server. A runner that hosts them says `experts` in its hello; the server answers it `hosting`, which experts of that runner it shows in at least one office, and the runner sends `experts`, its listing (name, project, subject and `state`: `starting`, `ready` or `failed`), only on a connection that has had a `hosting`, only while its link is up, and again when it changes. A session whose fact says `asksExperts` is sent `expert-rights`, the experts it may ask now. It asks with `ask-expert` (expert, question, `blocking`, and the tool call's id as `key`), polls with `ask-check` and acks the end with `asked-ack`, as for a room question; `asked` gains `expert`, an `EXPERT_*` `code`, and the `commit` and `branch` an answer describes. The server asks the host's runner with the `request` kind `answer-expert` (the question's own id as `questionId`, and the asking session as `asker`), which answers with the `reply` kind `answer-expert`, its citations in the answer, or refuses `unavailable` with an `expert` reason (`EXPERT_CAP`, with the cap, its limit and when it frees, `EXPERT_FORK_FAILED` or `EXPERT_UNKNOWN`). Names, subjects, answers and lists are bounded by `MAX_EXPERTS`, `MAX_EXPERT_SUBJECT_LENGTH` and `MAX_EXPERT_ANSWER_LENGTH`. An older side meets none of it: a server from before 0.13.0 drops the hello's `experts` and never sends `hosting`, so its runners never send `experts`, and it refuses `ask-expert` rather than asking a room; a runner or session plugin from before it doesn't say `experts` or `asksExperts`, so it is sent no `hosting`, `answer-expert` or `expert-rights`; and the new `asked` and `unavailable` fields are optional.
- **Experts' seniors, and hidden starts** (0.14.0): an expert's listing may say `senior`, that it has a senior generation its junior can ask; an older server ignores it. A server that reads it says `expertSenior` on every `hosting`, and only then does the runner send `expert-senior`, under the `answer-expert` request's `id` and with no text, when the junior answering it first asks its senior. A drive start in a folder may say `hidden`, never with mode `orca`: the session works in a clone Isoplan keeps for itself (a worktree of it, with `branch`), so the person's other tools don't list its folder. A runner that can says `hiddenStarts` in its hello, and only such a runner is sent `hidden`; one from before 0.14.0 would drop it and start in the person's own checkout. `EXPERT_ANSWER_WITHHELD` is gone from the expert codes: an expert refuses a secret-matched answer at once, so no released runner ever led a server to send it. An `asked` carrying it no longer parses, and code that names it no longer compiles.
- **Expert creation suggestions** (0.15.0): Isoplan suggests creating an expert where a session would have been helped by one. A session's facts may carry `areas` (`AreaFactSchema`): per repo-relative folder, the files read and searches made in it, their results' estimated tokens, the time they took and the person's corrections there; counts only, never contents or search patterns. A runner that can says `canCreateExpertsFromSuggestions` in its hello; the server sends it `expert-creation-suggestion-dismissals`, its person's dismissed areas (until a time, or forever), once its hello is let in and whenever they change, and the runner sends no expert creation suggestion messages on a connection before the first, so a server from before 0.15.0 is never sent one. The runner sends `expert-creation-suggestion` (a draft: key, subject, area, proof question and answer, and why it is suggested), `expert-creation-suggestion-ended` (`withdrawn`, or `no-draft`) and `expert-creation-progress` (`cloning`, `grounding`, `proof`, `ready` or `failed`). The server sends `create-expert-from-suggestion`, what the person confirmed, to one of their own runners, `draft-office-wide-expert-creation-suggestion`, asking for an office-wide expert creation suggestion on a folder several sessions searched, and `expert-creation-suggestion-ended` (`made`, with the expert's key; `dismissed`, only by a person on the floor; `refused`, a suggestion the office won't keep, such as one for a repo it doesn't take or someone else's session; or `expired`). `isDismissed(dismissals, project, folder, now)` is the one rule both sides use for whether a dismissal holds: one for the same project whose folder is that folder or one it is in (`.` every folder), for good or until a time later than now, letter case ignored. An expert's listing may say `areas`, the folders and globs it covers; `areaCovers(areas, folder)` is the one rule both sides use for whether they cover a folder: an area whose part before its first wildcard part is that folder or one it is in, `.` every folder, letter case ignored. Area paths are `AreaPathSchema`: relative, with forward slashes, never outside the repo. `expertDisplayName(key)` is the name people read (`pairing-tokens` is "Pairing Tokens Expert"). From 0.16.0 a session's `expert-creation-suggestion` may say `repetition`, what was done in its area again, which suggested it: its folder, the file read most, read in so many turns over so many sessions with so many of the area's files, or its folder searched so many times; counts only. An older runner sends none, and an older side ignores it.
- **`PROTOCOL_VERSION`**: the version both sides speak. A message's `v` must match it.
- **`projectId(remoteUrl, { machine, root })`**: a repository's project id, `host/owner/repo` from its git remote whatever form the remote is written in, or `local:<machine>/<root>` without one.

## Parse a message

```ts
import { parseDataLayerMessage } from "@isoplan/protocol";

const result = parseDataLayerMessage(JSON.parse(text));
if (result.ok) handle(result.message);
else if (result.kind === "unsupported-version") reply(result.error); // a peer on another protocol version
else drop(result.error);
```

`parseOfficeServerMessage` does the same for the other direction. Neither throws.
